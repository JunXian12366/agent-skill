# GPT 代码任务耗时诊断

## 适用边界

- 这是诊断工作流，不是模型加速器；不承诺减少多少时间，不修改代码、模型设置、权限、凭据或基础设施。
- 先从运行时元数据确认实际模型。不能仅凭用户称呼“ChatGPT”、技能名称或主代理模型推断子代理也是 GPT。
- 只对明确标识为 GPT 的执行区间做专项归因。模型未知时标注未知；其他模型区间单列，不纳入 GPT 对比。当前不是 GPT 时停止本技能，不擅自切换模型。
- 遵守适用的仓库指令；本技能不替代开发、审查或测试技能。不要为了测耗时启动应用、连接真实服务或重新执行有副作用的任务。

## 1. 先界定样本

1. 优先使用用户指出的最近任务；已有明确任务时不重复提问。
2. 记录任务类型、修改范围、开始/结束时间、主模型、子代理模型及可获得的推理强度。
3. 区分局部重构、业务开发、构建和大范围分析；不能直接用不同难度任务比较模型速度。
4. 只调查相关会话和时间范围，不扫描全部历史、全部仓库或无关用户目录。

## 2. 获取最小证据

1. 优先读取已有任务结果、构建报告和会话摘要；需要历史查询时，先使用可用的会话查询工具，按 session ID、时间范围过滤并限制结果。
2. 查询无数据不代表没有执行。必要时读取已知会话目录的本地事件日志，先确认事件结构，再按 UTF-8 流式解析。
3. 只提取时间戳、事件类型、调用 ID、父子关系、工具名、模型标识、成功状态和可用的用量字段。
4. 不打印原始日志全文、提示词、源码、环境变量、完整命令参数或敏感请求体；不上传本地日志到外部网站。
5. 无现成精确计时数据时，明确说明限制，不为了补数据反复重跑构建或安装监控工具。

## 3. 拆分耗时

| 类别 | 计量方式 | 不能推断的内容 |
|---|---|---|
| 任务墙钟时间 | 任务开始到最终交付，单列用户补充要求的时间 | 不能全部称为模型推理时间 |
| 工具往返 | 用同一调用 ID 配对 start/complete | 不等于磁盘、网络或命令自身耗时 |
| 构建/测试进程 | 进程起止或构建报告中的 duration | 初次等待超时不等于进程已结束 |
| 后台代理 | 启动到完成，并标注内部事件是否可见 | 不能把整段时间归为某次工具调用或某个模型 |
| 模型请求 | 仅使用已提供的排队、首 token、生成计时 | 不用事件空隙估算纯推理时间 |
| 用户交互/权限 | 可配对的请求与响应 | 不计为模型慢，不建议关闭安全保护 |
| 未归因区间 | 其余尚不能解释的时间 | 明确未知，不强行分配 |

- 并行工具使用时间区间并集；父代理、子代理、等待工具和其内部进程有重叠时，不能累加成总耗时。
- 等待工具的阻塞时间通常与后台工作重叠，不要据此断言轮询造成同等额外延迟。
- 多次模型请求与工具往返分别计数。汇总工具调用次数、中位数和最长值；样本充足才给 P95，并标注样本量。
- 区分本轮诊断自身的网络/工具耗时和被调查开发任务的耗时。

## 4. 按证据定位原因

依次判断：

1. 是否存在慢工具、权限等待、依赖下载、测试环境错误、连接超时或长尾请求。
2. 是否对小改动启动了不必要的完整代理流程、重复交接或重复探索。
3. 是否重复读取未变化的文件、搜索范围过大、输出过长或多次重复执行同一检查。
4. 是否因需求中途变化、修改错误或遗漏关联点导致返工。
5. 只有模型请求计时充分时，才分析 GPT 排队、推理强度、输出量或上下文开销；相关性不能当作因果。

工具失败后按可用能力和既有容错规则换用合适工具，避免相同失败请求无条件重试。异步任务仍在运行时读取原任务结果，不重复启动。

## 5. 输出可执行建议

- 首先给出证据最强的主要瓶颈，附任务范围和观测时间。
- 用小表列出证据、已知耗时、置信程度和具体改进；单独列出无法归因的部分。
- 优先推荐缩小探索范围、批量读取、保留上下文、合理委派和针对性验证，而不是跳过正确性检查。
- 如涉及模型/推理强度设置，只说明客户端实际支持的选项；由用户决定切换，不假装技能可以控制服务端推理速度。
- 需要验证优化效果时，建议在相同 GPT 型号、任务基准、权限和依赖缓存条件下做小规模对照；必须获授权且隔离执行，报告样本与波动。
- 不创建报告文件，除非用户明确指定；本次以只读诊断结论结束，不自动实施修复。
