# GPT 聚焦代码修改

## 适用边界

- 先确认当前实际模型属于 GPT；模型未知时不声称已启用 GPT 专项优化，非 GPT 时不应用本技能。
- 本技能优化执行流程，不改变业务要求、不降低正确性标准，也不能更改模型本身的速度。
- 保留并遵循适用的仓库规则与专业技能；例如 PMP Java 功能开发仍使用 `pmp-java-feature`，本技能仅补充效率约束。
- 对解释、方案、只读审查或未授权修复，不进入修改流程。不得擅自提交、部署、访问生产、修改凭据或用户配置。

## 1. 明确最小完整范围

1. 从用户请求提取目标行为、必须保持的行为、相关符号及验收条件。
2. 先读取适用指令、工作区状态及目标文件，保留已有改动。
3. 仅对影响实现方式的歧义提问，不要求每个小改动先审批计划。
4. 名称修正须覆盖声明、构造器、注入、调用方、关联测试及直接相关文档；不要因为是“小改动”漏掉连通关系。
5. 区分用户要求的改动与顺便重构，不为优化耗时擅自扩大或缩小业务范围。

## 2. 选择合适执行规模

| 任务 | 推荐处理 |
|---|---|
| 已知文件中的重命名、接口提取、局部条件调整 | 主代理直接处理；只有委派要求或明确收益时才交给其他代理 |
| 单一模块的完整功能 | 先集中查看入口、实现、直接依赖和相关测试，再成批修改 |
| 多个独立模块或研究问题 | 按互不重叠的范围并行；每个子任务明确交付和文件所有权 |
| 复杂并发、事务、契约或迁移 | 保留必要的深入分析和独立审查，不为追求快而省略 |

如更高优先级规则要求委派，遵循该规则，同时限制子代理探索范围，提供足够上下文，避免反复交接。

需要子代理时，明确指定客户端支持的 GPT 模型并核实实际使用情况；不可把默认子代理模型当作 GPT。客户端不能限定时，说明混合模型事实，不擅自修改全局配置。

## 3. 减少无效探索与输出

1. 优先使用代码智能或符号查找；没有时按文件名缩小范围，再做限定文件类型的文本搜索。
2. 独立文件读取、搜索和状态检查批量并行；手工编辑不与读取或其他编辑并发。
3. 已确认且未变化的事实可以复用；恢复会话、文件变化或准备修改时重新核对相关部分，不盲目复用旧内容。
4. 大文件只读所需范围，失败日志先看摘要和错误位置，不读取无关全文。
5. 不为本地代码问题默认查网页，不反复扫描全仓库，不创建无必要的计划、报告或辅助脚本。
6. 子代理拥有某范围期间不重复调查或修改同一范围；只有不同范围才并行。

## 4. 集中修改并检查连接关系

1. 理解目标方法与直接调用方后，再成批完成一个逻辑改动，避免猜测式微调。
2. 使用现有工具、依赖和模式；采用可审查的定点编辑，不用宽泛替换波及业务字符串或外部契约。
3. 重命名不自动改变路由、JSON 字段、数据库枚举值、Redis 键或错误语义；这些需要单独授权。
4. 调整控制流时核对异常隔离、执行顺序、过滤副作用、时间快照及缓存对象是否仍一致。
5. 发现方案不成立时先找原因再修正，不以增加默认值、吞异常或禁用检查掩盖问题。

## 5. 验证必须保留，但避免重复启动

1. 执行前先阅读所选测试，确认外部依赖隔离；使用仓库现有构建和测试工具。
2. 按仓库规则建立基线。只有同一相关源码状态下已有可核实结果、且适用规则允许时，才复用已有基线，并记录依据。
3. 所有相关文件修改完成后统一编译和运行相关测试；有失败则定位并修正，再运行受影响检查。
4. 验证范围由风险决定：局部改动优先定向测试，共享契约、基础设施或广泛影响应增加必要的全量回归；不以固定文件数作为免测理由。
5. 同一构建/测试还在运行时读取原进程结果，不因等待超时重复启动。
6. 已知测试语言、时区或依赖问题先核对证据。必要时仅在测试进程设置明确参数，不更改机器配置、不修改无关生产行为；失败仍如实记录。
7. 检查最终 diff、旧符号残留和验收条件。只有通过实际需要的检查才能结束；不能把“代码看起来正确”当作完成。

## 6. 防止任务无进展

- 连续多轮未获得新信息、重复读同一文件或反复运行同一失败命令时，暂停该策略，定位环境/契约/实现问题。
- 慢工具按既有容错规则处理；不要通过放宽权限或取消安全检查来提速。
- 不自动加载耗时诊断技能、收集全会话日志或增加监控开销；用户要求诊断，或有明确耗时问题需分析时，再使用 `gpt-latency-diagnose`。
- 小任务不反复发布进度，只在范围变化、真实阻碍或重要阶段转换时说明。
- 最终简明交付实际改动和必要限制，按当前输出约定报告验证情况；不宣称未经对照测量的性能提升。
